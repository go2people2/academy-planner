# 🌐 Hokma System — Shared Project Context

> 이 문서는 Hokma System을 구성하는 여러 프로젝트에서 공통으로 참조하는 아키텍처·데이터 경계·보안 원칙 문서입니다.
>
> 대상 프로젝트: **AMS**, **Fascan**, **Hokmanote**, **AMF**, 그리고 학생 오답 제출 기능인 **지혜의 노트** 관련 프로젝트/모듈.
>
> 목적은 각 프로젝트의 AI 에이전트와 개발자가 전체 생태계 안에서 자신의 책임, 연동 대상, 현재 구현 상태와 향후 계획을 혼동 없이 이해하도록 하는 것입니다.

---

## 1. 문서 사용 원칙

- 이 문서는 **공통 기준 문서**입니다. 각 프로젝트에는 별도의 `PROJECT_CONTEXT.md`를 두고, 해당 프로젝트의 실제 코드 구조·DB·API·배포·세부 규칙을 기록합니다.
- 공통 생태계의 역할·용어·데이터 경계가 바뀌면 이 문서를 먼저 갱신하고, 영향을 받는 프로젝트별 문서에 필요한 내용만 반영합니다.
- 문서에서 반드시 아래 상태를 구분합니다.
  - **현재 구현됨**: 실제 코드·DB·운영 환경에서 확인된 기능
  - **설계됨 / 향후 계획**: 방향은 정해졌으나 아직 구현·배포되지 않은 내용
  - **금지 사항 / 안전 규칙**: AI 에이전트와 개발자가 임의로 넘지 말아야 할 경계
- 확인되지 않은 테이블, API, 동기화 방식, 성능 수치, 배포 상태를 사실처럼 단정하지 않습니다.

## 2. 전체 생태계

Hokma System은 콘텐츠 생성, 학생 오답 수집, 오답 학습·클리닉, 미디어 제공, 학원 운영을 역할별 시스템이 분담하는 생태계입니다.

```text
Fascan
  → Data V3 콘텐츠 표준 생성
  → Hokmanote에 콘텐츠 기준 제공

AMS 학생 포털 `/<slug>/student`
  └─ 지혜의 노트
       → 학생별 오답 번호 제출
       → Supabase를 통한 Hokmanote 오답 학습 흐름 연동

Hokmanote
  ← Data V3 콘텐츠
  ← 학생별 오답 제출
  → 개인 맞춤 오답노트·학습 클리닉

AMF
  ← Data V3의 문항/미디어/Cue 참조
  → 원내 미디어 스트리밍

AMS
  → 학생·수업·출결·진도·숙제·테스트·보강·상담·리포트 관리
  → 학생 포털 및 지혜의 노트 제출 접점 제공
```

### 핵심 사실

1. **지혜의 노트**는 학생이 본인이 푼 교재에서 틀린 문항 번호를 선택해 제출하는 기능이며, AMS 학생 포털 `/<slug>/student`에 통합될 수 있습니다.
2. **Data V3**는 독립 앱이 아니라 Fascan이 생성하는 공통 콘텐츠 데이터 표준/구조입니다.
3. **Hokmanote**는 Data V3 콘텐츠와 학생별 오답 제출 데이터를 활용하는 디지털 오답노트·학습 클리닉 앱입니다.
4. **AMS**는 학원 운영과 학생 수업 맥락을 관리하는 시스템이며, Data V3 콘텐츠 생성 또는 Hokmanote의 오답노트 조판을 직접 대체하지 않습니다.
5. **AMF**는 콘텐츠 파일 저장·원내 네트워크 미디어 제공을 담당하는 엔진이며, AMS의 운영 데이터 책임과 분리됩니다.

## 4. Data V3 공통 정의

### Data V3의 성격

- Data V3는 Fascan이 생성하고 Hokmanote가 사용하는 **콘텐츠 데이터 표준**입니다.
- Data V3는 교재의 구조와 문항·미디어 연결을 표현하기 위한 공통 언어입니다.
- Data V3가 있다고 해서 모든 프로젝트가 즉시 같은 DB 또는 같은 저장소를 사용한다는 뜻은 아닙니다.
- 실제 공유 방식, DB 배치, API, 권한 모델, 동기화 주기는 프로젝트별 구현 문서와 승인된 설계에서만 정의합니다.

### 표준 영역

현재 공통 문맥에서 Data V3는 다음 5개 영역으로 설명합니다.

```text
master
unit_page
problems
media
media_sources
```

이 구조는 일반적으로 다음 관계를 표현합니다.

```text
교재
  → 단원 / 페이지
    → 문항
      → 문항 이미지 및 메타데이터
      → 관련 미디어 / 풀이 Cue 정보
```

### 콘텐츠 책임

- Fascan은 PDF와 가이드라인을 바탕으로 Data V3 콘텐츠를 생산합니다.
- Hokmanote는 Data V3를 읽어 학생별 오답 학습과 클리닉에 활용합니다.
- AMF는 허가된 Data V3 문항·미디어·Cue 참조를 바탕으로 원내 미디어 제공에 활용할 수 있습니다.
- AMS는 운영상 필요한 범위에서 Data V3 식별자 또는 참조 정보를 연결할 수 있지만, Data V3의 대용량 콘텐츠 전체를 무분별하게 중복 복제하지 않습니다.

## 5. AMS와 Data V3의 현재 관계

### 현재 구현 상태

> **중요: 현재 AMS의 Google Sheets/CSV 기반 `bookcode` 및 교재 리스트 구조는 Data V3가 아닙니다.**

- AMS는 현재 Google Sheets/CSV에서 가져오는 레거시 `bookcode` 및 교재 목록을 사용할 수 있습니다.
- AMS의 현행 `bookcode`를 Data V3 교재 식별자와 동일하다고 가정하면 안 됩니다.
- Google Sheets 기반 교재 구조가 Data V3의 5개 표준 영역과 동일하다고 가정하면 안 됩니다.
- Data V3가 아직 연결되지 않은 교재, 과거 교재, 운영 중인 수업 흐름이 존재할 수 있습니다.

### 향후 방향

AMS의 Data V3 연동은 **무중단 점진 전환**을 원칙으로 합니다.

- 레거시 Google Sheets/CSV `bookcode` 흐름을 일괄 삭제하거나 강제로 교체하지 않습니다.
- Data V3와 연결 가능한 교재부터 선택적으로 표준 식별자 또는 매핑을 연결합니다.
- Data V3 매핑이 없거나 조회에 실패하는 경우에도 기존 교재·수업 흐름이 계속 동작할 수 있어야 합니다.
- 기존 학생 배정, TodaySheet 진도, 숙제, 테스트, 오답 제출 기록은 유실되면 안 됩니다.
- 레거시 교재와 Data V3 기반 교재는 전환 기간 동안 공존할 수 있습니다.
- 실제 DB 변경, 테이블 추가, API 설계, 마이그레이션은 별도의 검토·승인 이후에만 진행합니다.

### 목표 상태의 역할 분리

```text
Fascan: Data V3 콘텐츠 생산
Hokmanote: Data V3 + 학생 오답 데이터 기반 학습·클리닉
AMF: 허가된 문항/미디어/Cue 기반 원내 미디어 제공
AMS: 수업·운영 맥락과 학생 포털 관리, 필요한 콘텐츠 참조 연결
```

## 6. 공통 보안과 데이터 경계

### 테넌트 격리

- 학생, 출결, 숙제, 상담, 성적, 수업 일지, 학생별 오답 제출 등 운영 데이터는 `academy_id` 기준으로 엄격히 격리해야 합니다.
- 한 학원의 사용자가 다른 학원의 학생 정보, 제출 내역, 교재 배정, 수업 기록, 상담 내용, 성적을 조회·수정할 수 없어야 합니다.
- 교재 콘텐츠가 공용으로 제공되는 경우에도 학생별 운영 데이터까지 공유되어서는 안 됩니다.

### 공용 콘텐츠와 전용 콘텐츠

- 공용 콘텐츠와 특정 학원 전용 콘텐츠를 구분해야 합니다.
- 특정 학원 전용 교재, PDF, 문항 이미지, 영상 URL, 자체 제작 콘텐츠는 권한이 없는 다른 테넌트에 노출되어서는 안 됩니다.
- 콘텐츠의 소유권·사용 권한·저작권 경계는 운영 데이터의 테넌트 격리와 별도로 명시적으로 검증해야 합니다.

### 서버 인가와 입력 검증

- 클라이언트가 전달한 `academy_id`, `student_id`, 교재 ID, 문항 ID, 콘텐츠 경로를 그대로 신뢰하지 않습니다.
- API와 Supabase RLS는 로그인 주체, 대상 학생, 대상 운영 기록, 대상 콘텐츠의 권한·테넌트 일치를 검증해야 합니다.
- 학생 오답 제출은 학생이 본인의 범위 안에서만 제출하도록 검증하며, 다른 학생의 제출 데이터를 읽거나 변경할 수 없어야 합니다.
- 쓰기 작업은 가능한 한 서버 측 권한 검증과 원자적 처리 원칙을 적용합니다.

### 개인정보와 비밀정보

- 학생 이름, 연락처, 결석 사유, 상담 내용, 성적 본문, 오답 상세 등 개인정보·민감 학습 기록을 문서 예시, 오류 메시지, 로그, 콘솔 출력에 그대로 남기지 않습니다.
- API key, service role key, DB 비밀번호, 토큰, 내부망 주소, 개인 식별 가능한 운영 데이터는 코드·문서·로그에 평문으로 기록하지 않습니다.
- 읽기 전용 점검 보고에는 필요한 구조적 사실과 위험 사유만 기록하고, 개인 식별자와 기록 본문은 제외합니다.

## 7. AI 에이전트 작업 규칙

각 프로젝트의 AI 에이전트는 작업 전 이 문서와 해당 프로젝트의 `PROJECT_CONTEXT.md`를 함께 확인해야 합니다.

1. **최소 변경 원칙**: 전체 리팩터링보다 현재 문제를 해결하는 가장 작은 변경을 우선합니다.
2. **경계 존중**: 다른 시스템의 책임을 침범하는 코드·DB 설계를 임의로 추가하지 않습니다.
3. **현재와 계획 분리**: 아직 구현되지 않은 통합, 자동화, API, DB 구조를 현재 기능처럼 설명하거나 전제하지 않습니다.
4. **레거시 보호**: Data V3 전환을 이유로 기존 Google Sheets/CSV, `bookcode`, 기존 수업 기록, 학생 배정 데이터를 일괄 삭제·강제 변환하지 않습니다.
5. **DB/RLS 사전 승인**: Supabase 스키마, RLS, RPC, 운영 데이터 수정은 영향·테넌트 격리·롤백·테스트 계획을 먼저 제시하고 명시적 승인 후 진행합니다.
6. **배포 분리**: 코드 변경 승인과 production 배포 승인은 별도 단계로 다룹니다.
7. **개인정보 보호**: 디버그·보고·문서에서 학생 개인정보, 수업 기록 본문, 비밀키를 출력하지 않습니다.
8. **검증 우선**: 수정 전 관련 타입·호출 경로·권한 경계를 확인하고, 수정 후 최소한 타입 검사와 영향 범위 테스트를 수행합니다.

## 8. 프로젝트별 문서 작성 안내

각 프로젝트의 `PROJECT_CONTEXT.md`에는 이 공통 문서를 반복 복사하기보다 다음을 중심으로 기록합니다.

```text
- 프로젝트의 실제 기술 스택과 폴더 구조
- 현재 구현된 기능과 확인된 데이터 흐름
- 해당 프로젝트가 읽고 쓰는 데이터의 소유권·권한·테넌트 규칙
- 다른 프로젝트와 연결되는 입력·출력 계약
- 현재 레거시 호환 방식과 fallback 정책
- 프로젝트 고유의 금지 사항, 테스트 절차, 배포 규칙
- 향후 계획과 미구현 범위
```

프로젝트별 문서에는 반드시 다음 구분을 유지합니다.

```text
[현재 구현됨]
[설계됨 / 미구현]
[금지 사항 / 안전 규칙]
```
